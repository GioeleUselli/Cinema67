🪑 Sistema Posti (Hold Management)

Problema: Race Condition

Cosa succede se 2 utenti cercano di prenotare lo stesso posto contemporaneamente?

// 👤 User 1 → T=0s: SELECT Seat WHERE ShowId=5 AND Status=AVAILABLE // 👤 User 2 → T=1s: SELECT Seat WHERE ShowId=5 AND Status=AVAILABLE (stesso risultato!) // 👤 User 1 → T=2s: UPDATE Seat SET Status=HOLD ✓ OK // 👤 User 2 → T=3s: UPDATE Seat SET Status=HOLD ✓ Oops, conflitto! // ✅ SOLUZIONE: SERIALIZABLE Isolation Level // ✅ Transactions prevent race conditions // ✅ Database locks ensure atomicity

Soluzione Implementata

1. Database Layer

  • Composite key: (ShowId, SeatId)
  • Status: AVAILABLE, HOLD, SOLD
  • HoldTokenExpiry: datetime
  • RowVersion: optimistic concurrency

2. Transaction Control

  • BEGIN TRANSACTION
  • Lock seats for update
  • Verify still available
  • Update status + TTL
  • COMMIT or ROLLBACK

Hold Lifecycle

T=0s: User selects seats → Status = HOLD, HoldExpiry = NOW + 10min
T=60s: Client keep-alive → HoldExpiry extended to NOW + 10min
T=5min: Background cleanup service runs → Finds HoldExpiry < NOW
T=10min: If no payment → Status = AVAILABLE, HoldToken = NULL
T=10min+: Seat available for other users immediately

JWT Token Flow

1. User logs in with email + password 2. Backend verifies BCrypt(password_hash) 3. Creates JWT: { sub: userId, email, role, exp: NOW+15min } 4. Returns: { accessToken, refreshToken } 5. Client stores in localStorage + schedules refresh 6. Auto-refresh at T=14:50min (before expiry) 7. On 401 → POST /auth/refresh → New tokens

💳 Integrazione Stripe (Payment Processing)

Flusso Pagamento

1. Create PaymentIntent

POST /stripe → Create intent { amount, currency, idempotencyKey }

2. Client-side Confirmation

User enters card details → confirmCardPayment(clientSecret)

3. 3D Secure Challenge

If required → Bank sends 2FA code → User confirms

4. Webhook Notification

Stripe → POST /webhooks/stripe → charge.succeeded

5. Order Confirmation

Mark Ordine = PAID, Generate Tickets, Send Email

⚠️ Protezioni Anti-Frode

  • Idempotency Keys: Stessa richiesta 2 volte = stesso risultato (no double-charge)
  • 3D Secure: Verifica aggiuntiva per transazioni sospette
  • Webhook Verification: Firma HMAC su ogni webhook per prevenire spoofing
  • PCI-DSS Compliant: Stripe gestisce dati sensibili (no stock locale)
💰 Multi-Payment Support:
  • Internal Credit: User ha saldo → Deduct diretto (no fees)
  • Stripe Card: Credit/Debit card (2.9% + €0.30 fee)
  • Split Payment: Combina credit + card se necessario

📱 QR Code Generation & Validation

Generazione QR (Backend)

// QRPayload structure { "ticketId": 1245, "userId": 42, "showId": 123, "seatId": 456, "timestamp": "2024-12-25T20:30:00Z", "hash": "sha256(ticketId|userId|secret)" // Anti-tampering } // Encoded in Base64 → QR code image (300x300px) // Error correction level: H (30% recovery) // Embedded in PDF + sent via email

Validazione QR (Cinema Entrance)

✅ Verifiche Di Sicurezza:
  1. Decode QR payload
  2. Verify hash (anti-tampering)
  3. Check NOT already scanned
  4. Verify show time
  5. Grant entry
❌ Scenari Rifiuto:
  1. Double scan → Alert staff
  2. Invalid hash → Possible forgery
  3. Show expired → Time check
  4. Invalid ticket ID
  5. Wrong cinema/show
📊 Audit Trail:
  • Every scan logged with: userId, ticketId, timestamp, cinema location
  • Double-entry attempts flagged for investigation
  • Analytics: Attendance tracking in real-time
